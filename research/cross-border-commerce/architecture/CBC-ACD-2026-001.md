# 3. Contract Design Principle

Every Cross-Border Commerce contract SHALL preserve:

```text
semantic ownership
evidence provenance
unknown state
jurisdiction context
destination context
derivation state
confidence / completeness state
```

A downstream authority SHALL NOT reinterpret missing evidence as a
known value merely because its contract allows a field to be absent.

---

# 4. Canonical Contract Set

The initial contract set consists of:

```text
1. Cross-Border Evaluation Context Contract

2. Evidence Provenance Contract

3. Regulatory Gate Contract

4. Shipping-Route Intelligence Contract

5. Landed-Cost Intelligence Contract

6. Cross-Market Comparison Contract

7. Recommendation Evidence Contract
```

These are architecture contracts.

They are not yet Python models, APIs, schemas, tables, or wire formats.

---

# 5. Cross-Border Evaluation Context Contract

## 5.1 Purpose

The Cross-Border Evaluation Context provides the minimum canonical
context required to evaluate a cross-border commerce candidate.

## 5.2 Required Semantic Fields

```text
origin jurisdiction
destination jurisdiction
destination country
candidate identity reference
marketplace reference
evaluation time
```

## 5.3 Optional / Unknown-Capable Fields

```text
destination region
user delivery preference
shipping destination class
currency context
comparison group
route preference
```

Unknown values must remain explicitly representable.

## 5.4 Must Not Contain

The context contract must not become the owner of:

```text
general user preference
general session state
general product identity
general recommendation policy
payment information
transaction state
```

It references those authorities when required.

# 6. Evidence Provenance Contract

Every cross-border evidence item must be able to preserve at minimum:

```text
evidence identifier
source identifier
source type
observation time
effective time
jurisdiction
freshness state
derivation state
authority class
availability state
confidence state
```

Evidence classification must support the conceptual distinction:

```text
OBSERVED
AUTHORITATIVE
DERIVED
ESTIMATED
NON_AUTHORITATIVE
UNKNOWN
UNAVAILABLE
STALE
```

The final vocabulary may be refined later, but provenance loss is not
permitted.

---

# 7. Unknown-State Contract

Every architecture contract that may receive incomplete evidence must
support:

```text
KNOWN
ESTIMATED
DERIVED
UNKNOWN
UNAVAILABLE
NOT_APPLICABLE
```

No contract may imply:

```text
UNKNOWN == ZERO
UNKNOWN == FALSE
UNKNOWN == ELIGIBLE
UNKNOWN == AVAILABLE
```

unless a separate rule provides authoritative evidence for that state.

# 8. Regulatory Gate Contract

## 8.1 Input

The Regulatory Gate consumes:

```text
product / category identity evidence
origin jurisdiction
destination jurisdiction
regulatory evidence
effective-date evidence
source authority evidence
```

## 8.2 Output

The Regulatory Gate must be able to return:

```text
ELIGIBLE
INELIGIBLE
CONDITIONAL
UNKNOWN
INSUFFICIENT_EVIDENCE
NOT_APPLICABLE
```

## 8.3 Output Evidence

A regulatory decision must preserve:

```text
decision state
evidence references
jurisdiction
effective time
confidence / sufficiency state
reason
unknown / missing evidence
```

## 8.4 Safety Rule

If material regulatory evidence is unavailable:

```text
ELIGIBLE
```

must not be produced solely by default.

## 8.5 Must Not Perform

```text
legal advice
customs filing
regulatory filing
brokerage execution
government decision execution
```

## 9.1 Input

```text
origin
destination
candidate / seller shipping evidence

forwarder evidence
regulatory eligibility state
route constraints
```

## 9.2 Output

A route result may represent:

```text
DIRECT
FORWARDER
MULTI_LEG
UNAVAILABLE
UNKNOWN
```

with supporting information for:

```text
route legs
carrier / forwarder references
availability
estimated timing
estimated cost
constraints
evidence provenance
completeness
```

## 9.3 Execution Boundary

The contract provides intelligence only.

It must not perform:

```text
shipment booking
carrier dispatch
warehouse execution
package consolidation execution
delivery execution
```

# 10. Landed-Cost Intelligence Contract

## 10.1 Input Components

Landed-Cost Intelligence may consume:

```text
item price evidence
shipping-route result
international shipping evidence
forwarding evidence
duty evidence
tax evidence
service-fee evidence
currency context
regulatory state
```

## 10.2 Cost Components

A landed-cost result must allow distinct representation of:

```text
item price
international shipping
forwarding cost
duty
tax
service fees
other known route costs
```

## 10.3 Component State

Every material cost component must carry one of:

```text
KNOWN
ESTIMATED
DERIVED
UNKNOWN
UNAVAILABLE
NOT_APPLICABLE
```

## 10.4 Overall Completeness

The result must be able to distinguish:

```text
COMPLETE
PARTIAL
ESTIMATED
UNKNOWN
```

## 10.5 False-Precision Prevention

A numeric total SHALL NOT be represented as fully complete when a
material cost component remains unknown.

Therefore:

```text
unknown duty != zero duty
unknown tax != zero tax
unknown shipping != free shipping
```

## 11.2 Comparison Inputs

```text
identity / relationship evidence
marketplace evidence
product evidence
landed-cost result

quality / value / trust evidence
```

## 11.3 Comparison Output

The comparison result may include:

```text
candidate references
relationship type
market context
cost comparison
availability comparison
regulatory comparison
route comparison
quality / value / trust evidence
evidence completeness
unknown state
```

## 11.4 Boundary

Cross-Market Comparison must not own final recommendation policy.

# 12. Recommendation Evidence Contract

Cross-Border Intelligence supplies structured evidence to the canonical
Recommendation Engine.

The contract may provide:

```text
destination context
candidate eligibility
landed cost
cost completeness
shipping route
shipping availability
cross-market comparison
regulatory state
evidence provenance
uncertainty state
```

The canonical Recommendation Engine remains responsible for:

```text
general recommendation policy
ranking semantics
priority policy
final recommendation selection
```

unless a later architecture decision explicitly changes that authority.

---

# 13. Product Identity Contract Boundary

Cross-Border Intelligence requires identity or relationship evidence but
does not own general Product Identity.

The dependency direction is:

```text
Canonical Product Identity
        ->
Identity / Relationship Evidence
        ->
Cross-Market Product Comparison
```

not:

```text
Cross-Market Product Comparison
        ->
Canonical Product Identity
```

This boundary is mandatory.

---

# 14. Marketplace Contract Boundary

Marketplace Core remains authoritative for general marketplace evidence
and normalization where already established.

The dependency direction is:

```text
Marketplace Core
        ->
Marketplace Evidence
        ->
Cross-Border Intelligence
```

Cross-Border Intelligence may interpret that evidence in a
destination-aware cross-border context.

It must not redefine Marketplace Core semantics.

---

# 15. Market Intelligence Contract Boundary

Market Intelligence remains authoritative for general market-level
signals.

The dependency direction is:

```text
Market Intelligence
        ->
Market Evidence
        ->
Cross-Border Comparison / Recommendation Evidence
```

Cross-Border Commerce does not acquire ownership of general market
intelligence.

---

# 16. Experience Architecture Contract Boundary

Cross-Border Intelligence may produce experience-relevant state such as:

```text
cost completeness
regulatory uncertainty
shipping availability
route uncertainty
evidence confidence
destination context
```

Experience Architecture remains responsible for approved presentation
and user-experience semantics.

Therefore:

```text
Cross-Border Intelligence
        ->
Experience Evidence / State

Experience Architecture
        ->
Presentation Semantics
```

---

# 17. Preference Contract Boundary

Preference remains authoritative for persistent user preference.

Cross-Border Intelligence may consume canonically available preference
signals.

The dependency direction is:

```text
Preference
        ->
Preference Evidence
        ->
Cross-Border Evaluation
```

Cross-Border Intelligence SHALL NOT maintain a parallel canonical user
preference authority.

---

# 18. Session Context Contract Boundary

Session Context remains authoritative for temporary interaction state.

Cross-Border Commerce may consume:

```text
current destination
current query
current comparison context
temporary filters
```

where those concepts are canonically represented.

Cross-Border Commerce SHALL NOT create competing session ownership.

---

# 19. Food / Product Knowledge Contract Boundary

Food Knowledge and Product Intelligence remain authoritative for
intrinsic product-domain knowledge.

Cross-Border Intelligence may consume that knowledge.

The distinction is:

```text
Intrinsic Product Knowledge
        ->
Existing Product / Food Authority

Cross-Border Eligibility / Route / Cost
        ->
Cross-Border Intelligence
```

The intended high-level dependency direction is:

```text
Existing Canonical Authorities
        |
        v
Canonical Evidence
        |
        v
Cross-Border Intelligence
        |
        +--> Regulatory Gate
        |
        +--> Shipping-Route Intelligence
        |
        +--> Landed-Cost Intelligence
        |
        +--> Cross-Market Comparison
        |
        v
Cross-Border Recommendation Evidence
        |
        v
Canonical Recommendation Engine
        |
        v

```

Dependency direction must not imply ownership reversal.

# 21. Evidence-First Contract Rule

No derived cross-border result is authoritative merely because it is
produced by a canonical component.

Each derived result must remain connected to:

```text
input evidence
provenance
derivation state
unknown state
completeness
```

Architecture consumers must be able to distinguish evidence quality.

---

# 22. Regulatory Fail-Closed Intelligence Rule

Where regulatory eligibility materially affects a recommendation and
evidence is insufficient, the contract must support:

```text
UNKNOWN
INSUFFICIENT_EVIDENCE
CONDITIONAL
```

rather than manufacturing positive eligibility.

This is an intelligence safety boundary, not transaction execution.

---

# 23. Landed-Cost Contract Rule

A landed-cost value without completeness metadata is not sufficient as a
canonical landed-cost result.

Canonical landed-cost evidence must include:

```text
component values
component states
overall completeness
evidence provenance
currency context
evaluation context
```

---

# 24. Destination Context Rule

Cross-border outputs are context-dependent.

Every material result that can vary by destination must remain tied to
its destination context.

Examples include:

```text
regulatory eligibility
shipping availability
shipping cost
duty
tax
route feasibility
landed cost
```

A result derived for one jurisdiction must not silently be reused as
valid for another jurisdiction.

---

# 25. Freshness Rule

Evidence that can materially change over time must preserve freshness
information.

Potentially time-sensitive evidence includes:

```text
price
availability
shipping cost
carrier availability
forwarder fees
duty rules
tax rules
restricted-item rules
exchange rates
delivery estimates
```

The exact canonical freshness policy requires subsequent governance.

---

# 26. Currency Boundary

Landed-cost comparison may require currency normalization.

This architecture contract recognizes the requirement but does not yet
assign a permanent canonical currency authority.

Any future currency conversion contract must preserve:

```text
source currency
target currency
exchange-rate source
rate observation time
rate provenance
conversion state
```

No implementation authority is granted by this recognition.

---

# 27. Contract Failure States

Cross-border contracts must permit meaningful failure states rather
than relying only on exceptions or empty values.

Conceptual states may include:

```text
VALID
PARTIAL
UNKNOWN
INSUFFICIENT_EVIDENCE
UNAVAILABLE
INELIGIBLE
STALE
```

The final vocabulary remains subject to architecture review.

---

```text
order placement
purchase execution
customs filing
brokerage execution
warehouse execution
shipment booking
carrier dispatch
delivery execution

```

Cross-Border Commerce remains an intelligence and recommendation

# 31. Contract Review Questions

The next architecture review must resolve at minimum:

```text
1. Which conceptual states become canonical enums?

2. Which evidence fields are mandatory across all contracts?

3. Whether Cross-Border Evidence Provenance is domain-local or a
   reusable institution-wide evidence capability.

4. Whether Regulatory Evidence remains commerce-local or should become
   a reusable institutional authority.

5. Whether Landed-Cost Intelligence remains subordinate to
   Cross-Border Intelligence or becomes a commerce-wide canonical
   authority.

   EQUIVALENT / SUBSTITUTE evidence.

8. Which freshness requirements are architecture-wide.

   evidence without producing false certainty.

    the underlying evidence semantics.
```
