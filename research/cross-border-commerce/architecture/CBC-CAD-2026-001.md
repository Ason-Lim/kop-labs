# 4. Decision 1 — Canonical Evidence State Vocabulary

## 4.1 Decision

The following canonical evidence-state vocabulary is established:

```text
KNOWN
ESTIMATED
DERIVED
UNKNOWN
UNAVAILABLE
NOT_APPLICABLE
```

These states describe the epistemic or availability condition of
evidence.

## 4.2 Meanings

```text
KNOWN

A value supported by sufficient evidence for the current evaluation
context.


ESTIMATED

A value produced by an estimation process and explicitly identified as
an estimate.


DERIVED

A value computed or inferred from other evidence while preserving its
derivation lineage.


UNKNOWN

A value whose correct state or value cannot currently be established.


UNAVAILABLE

Evidence is expected or relevant but cannot currently be obtained.


NOT_APPLICABLE

The field or condition does not apply to the evaluation context.
```

## 4.3 Boundary

The following equivalences are prohibited:

```text
UNKNOWN != ZERO

UNKNOWN != FALSE

UNKNOWN != ELIGIBLE

UNKNOWN != AVAILABLE

UNAVAILABLE != NOT_APPLICABLE
```

## 4.4 Canonical Owner

The vocabulary is owned by the Cross-Border Commerce architecture
contract baseline for current use.

Its potential reuse beyond Cross-Border Commerce remains open for
future institution-wide evidence governance.

## 4.5 Implementation Impact

```text
IMPLEMENTATION:
NOT AUTHORIZED
```

The decision does not authorize enums, models, schemas, or code.

# 5. Decision 2 — Regulatory Decision Vocabulary

## 5.1 Decision

The Regulatory Gate canonical result states are:

```text
ELIGIBLE
INELIGIBLE
CONDITIONAL
UNKNOWN
INSUFFICIENT_EVIDENCE
NOT_APPLICABLE
```

## 5.2 Safety Rule

Positive eligibility SHALL NOT be produced when material evidence is
missing or insufficient.

Therefore:

```text
insufficient regulatory evidence
        ->
UNKNOWN
or
INSUFFICIENT_EVIDENCE
or
CONDITIONAL
```

not:

```text
insufficient regulatory evidence
        ->
ELIGIBLE
```

## 5.3 Canonical Owner

The decision vocabulary is owned by the Cross-Border Regulatory Gate
architecture responsibility.

The underlying source evidence may originate from external regulatory
authorities.

## 5.4 Boundary

The Regulatory Gate does not become:

```text
legal authority
customs authority
government authority
brokerage authority
filing authority
```

It evaluates evidence for intelligence purposes.

# 6. Decision 3 — Mandatory Evidence Fields

## 6.1 Decision

Every material cross-border evidence record must be capable of
preserving the following canonical metadata:

```text
evidence identifier
source identifier
source type
observation time
effective time
jurisdiction
authority class
derivation state
availability state
freshness state
```

Where applicable, it should additionally preserve:

```text
confidence state
destination context
origin context
currency context
source reference
derivation references
```

## 6.2 Rationale

Cross-border decisions can change with:

```text
time
jurisdiction
destination
source authority
currency
regulatory state
shipping conditions
```

Evidence without sufficient provenance cannot safely support canonical
cross-border conclusions.

## 6.3 Boundary

Not every evidence item must contain a numeric confidence score.

The architecture requires confidence state representation where
material, but does not mandate a universal probability model.

# 7. Decision 4 — Evidence Authority Class

## 7.1 Decision

Evidence must be able to distinguish authority classes.

The minimum conceptual classes are:

```text
AUTHORITATIVE
NON_AUTHORITATIVE
DERIVED
ESTIMATED
UNKNOWN
```

## 7.2 Clarification

`DERIVED` and `ESTIMATED` describe evidence creation state and may
coexist conceptually with source authority information.

Therefore later implementation design must avoid treating the list as a
single mutually exclusive technical enum without architecture review.

## 7.3 Decision

The architecture SHALL preserve separate concepts for:

```text
source authority
derivation state
availability state
freshness state
```

These dimensions must not be collapsed into one field.

```text

availability
shipping cost
carrier availability

exchange rates

tax rules

delivery estimates
```

## 14.2 Required Freshness Metadata

Where materially applicable, evidence must preserve:

```text
observation time
effective time
freshness state
source identity
```

## 14.3 Canonical Freshness States

The minimum conceptual freshness states are:

```text
CURRENT
STALE
UNKNOWN_FRESHNESS
NOT_APPLICABLE
```

## 14.4 Policy Boundary

This document does not define universal time thresholds such as:

```text
price stale after X minutes
```

## 14.5 Decision

Freshness thresholds require a separate governed policy or
source-specific contract.

# 16. Decision 13 — Landed-Cost Completeness Vocabulary

## 16.1 Decision

The canonical landed-cost completeness states are:

```text
COMPLETE
PARTIAL
ESTIMATED
UNKNOWN
```

## 16.2 Meaning

```text
COMPLETE

All material cost components required for the current evaluation context
are known or supported as not applicable.


PARTIAL

One or more material components remain unknown or unavailable while
some cost evidence is available.


ESTIMATED

Material components or the resulting total rely on explicit estimation.


UNKNOWN

A meaningful landed-cost result cannot currently be established.
```

## 16.3 Safety Rule

A numeric value SHALL NOT imply `COMPLETE`.

Completeness metadata is mandatory for canonical landed-cost results.

```text
unknown tax != zero tax
```

# 18. Decision 15 — Recommendation Consumption of Partial Evidence

## 18.1 Decision

The Recommendation Engine may consume partial cross-border evidence.

However, it must receive sufficient state to distinguish:

```text
complete evidence
partial evidence
estimated evidence
unknown evidence
regulatory uncertainty
```

## 18.2 Boundary

Cross-Border Intelligence must not convert partial evidence into false
certainty before passing it to Recommendation Engine.

Recommendation Engine must not assume a numeric landed cost is complete
without completeness evidence.

## 18.3 Ownership

```text
Cross-Border Intelligence:
owns cross-border evidence state

Recommendation Engine:
owns final recommendation policy
```

semantics to commerce-specific business logic.

Cross-border architecture contracts must support meaningful failure or
insufficiency states.

The canonical conceptual set includes:

```text
VALID
PARTIAL
UNKNOWN
INSUFFICIENT_EVIDENCE
UNAVAILABLE
INELIGIBLE
STALE
```

These states describe contract result condition.

They are distinct from evidence-state vocabulary.

A later implementation design must not collapse:

```text
evidence state
regulatory decision state
freshness state
result condition
```

into a single enum.
